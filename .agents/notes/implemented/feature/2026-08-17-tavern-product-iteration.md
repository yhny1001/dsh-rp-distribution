# Tavern-style RP product iteration

Date: 2026-08-17. Status: implemented locally.

## Decision

`@dsh-rp/product` owns a Tavern-style resource and conversation experience without becoming a second Harness. Product state schema v2 adds Prompt Manager presets, imported provenance, Character Card greetings/examples/tags, and per-Session transcript annotations. The Bundle reuses `@dsh-rp/compat-sillytavern` as its clean-room parser and bundles that adapter plus its binary dependencies, so an installed product Tarball does not require the complete RP distribution family.

Prompt presets retain up to 1,024 definitions and each order uses up to 256 fixed System Prompt seats because Cordis registrations are effects while user order is mutable data. Unassigned definitions remain available for later insertion. Common markers resolve to separately owned system, world, character, persona, scene, example, and chat-history material. A safe pure-text macro pass resolves character/persona names and ordered `setvar/getvar` assignments without granting TavernHelper or regex execution. The `agent/request` waterfall calls `next()` before applying supported generation overrides; Request Header events remain the durable model-request record. The built-in default output cap is 8,192 tokens, while an imported `openai_max_tokens` value is preserved exactly. ST `min` reasoning is stored as normalized DSH `minimal`; request assembly resolves the selected exact provider/model and applies that override only when its capability metadata advertises `minimal`, otherwise retaining the selection returned by `next()` or the provider default.

## Transcript ownership and edits

The DSH Session log remains immutable and authoritative. The product records only the persona or primary character selected when an append-origin user or assistant message lands, plus later edit metadata. The RP view combines those annotations with the Host conversation snapshot, so changing the current primary character never relabels earlier messages.

A user edit targets the current Surface node and cites that node plus its known provenance. Core permits `user/message` replacement outside an open Step but requires every `assistant/message` to name the currently open turn and Step. The product therefore cannot append an assistant rewrite while the user is editing an idle conversation. It writes an explicitly framed `plugin/recall` user-role node that identifies the content as edited assistant history, while the RP transcript preserves the original character role. This makes later model calls consume the edited body without modifying AgentLoop or falsely claiming human authority.

## Import behavior

The local API accepts a bounded batch of Character Card JSON/PNG/CHARX, World Info, Persona, and Chat Completion preset documents. Each file is parsed independently and reported explicitly; successful siblings commit as one optimistic product-state revision even when another file is invalid. PNG card bytes are content-addressed, written beside product state, and served only through a validated same-origin asset id. The Client's shared Avatar Face base class constrains image dimensions, overflow, `cover` cropping, and portrait focus for every use, so a business surface cannot bring the original dimensions into page layout. Raw CHARX embedded bytes remain inert. Script, regex, remote-resource, and unknown extension behavior remains inert according to the compatibility adapter report.

Preset import is deliberately two-track. The lossless source document remains attached to an immediately selectable `sillytavern` preset. The UI then asks whether to create a separate `harness` adaptation; accepting creates or refreshes a deterministic sibling without replacing the source. The adaptation retains definitions, selected order, switches, roles, markers, content, safe variables, and generation settings while removing ST injection metadata that the current Host cannot execute. Both entries remain selectable per Session, and the adaptation records its source id, conversion time, normalized-field count, inert-extension count, and notes.

The product now distinguishes Tavern Chat from Agent RP at the Agent-preset layer. `rp-tavern` mounts prompt assembly without domain tools. `rp-agent` mounts the same imported Prompt preset with atomic `rp_commit_turn`, read-only `rp_read_state`, and compatible `rp_update_state`/`rp_propose_choices`. Native tool calls/results remain durable evidence while product state projects into later request headers and the world-state board. World Info entries retain keys, secondary keys, constant flags, switches, and priority in the editor. Model compliance is not yet a hard invariant: the strengthened Agent prompt requires a Ledger commit before prose, but a State Keeper Sidecar must eventually audit missing commits at the Turn boundary.

Before a Session exists, the native new-session Agent Preset Seat keeps its staged selection inside its own component, so another plugin cannot read it and an RP binding has no Agent that can receive a command. The product therefore contributes a compatible higher-priority Preset Seat that retains every healthy deployment preset while sharing its selection with RP quick setup. Tavern and Agent both expose Prompt preset, Character Card, persona, lorebook, and scene controls; only Agent exposes Experience. Applying asks the Workspace Runtime to reuse or create a blank Session, waits until its client binding exists, applies the staged preset, and then submits the existing `rp-studio-bind` command. Standard coding presets produce no RP surface.

## Verification

Focused tests cover Prompt Manager ordering and markers, a 210-definition/177-switch/56-enabled preset, lossless source retention and non-destructive adaptation, generation settings, safe macros, PNG asset persistence, mixed imports, revision serialization, activation rollback, speaker capture, and provenance-complete Surface edits. The actual Tarball is installed into an isolated DSH `0.1.0-rc.6` Web profile. Codex in-app Browser verification first imports two Character Cards plus one preset beside one invalid file, then imports the user's 3.4 MiB CCv3 PNG and 453 KiB 210-definition preset. The real preset exposes 177 independent switches, 56 source-enabled entries, 33 unassigned definitions, maxTokens 30,000, and two disabled-behavior warnings; its real request header logs temperature 1, maxTokens 30,000, a 10,511-character assembled system Prompt, and no unresolved double-brace macros. The import result asks whether to adapt; accepting leaves `[ST COMPAT] Izumi 0814.json` intact, creates `[Harness] Izumi 0814.json · Harness`, selects the copy, and successfully runs another real model call. A real model call replies as the PNG card's named character. The earlier verification also edits a reply, proves the next model call uses the edited body, switches the primary character, and proves old and new replies retain different speaker names.

The reasoning regression uses an imported `minimal` preset against two model routes. A Kaon-like route advertising only `high` preserves its existing `high` selection or provider default instead of submitting `minimal`; a route explicitly advertising `minimal` receives the imported override. Both paths traverse the same `agent/request` waterfall and prove that exact provider/model identity plus the Turn signal reaches capability resolution.

The repaired Tarball is reinstalled into the isolated Web profile and calls `kaon/deepseek-v4-flash-0731` again in the same Agent RP Session that retains the historical `UNSUPPORTED_REASONING_EFFORT` record. The new request uses the Izumi Harness preset, Katisia, and the existing world resources, completes in eight seconds, and returns a Chinese scene confirmation without another reasoning-effort refusal.

The same real PNG is visually regressed in both native Conversation and RP Conversation tabs. Its portrait no longer escapes the newly added selected-composition avatar into the Session background; it appears only in the 28px selected avatar, the RP header avatar, and per-character message avatars, all with a square face-focused crop.

The Agent RP browser run selects `rp-adaptive` with the real Card and Harness-adapted Izumi preset. The model performs three state calls (time, scene, memory), proposes three choices, and then emits the character reply. The RP view renders TIME, SCENE, MEMORY cards plus the three buttons. Clicking “调查港口” submits the stored prompt as the next native user message and produces another model turn. A separate World Info import verifies three preserved entries, two enabled switches, search, and per-entry editing.

The blank landing-page run selects Tavern Chat and Agent RP in turn. Both show Prompt preset, Character Card, persona, lorebook, and scene controls; Tavern omits Experience, Agent shows all five Experience choices, and the mode label and apply action update with the selection. The run then applies the real Harness-adapted Izumi preset, Katisia card, `user` persona, Rinascita lorebook, and scene text. Workspace Runtime creates a blank Session, the surface collapses into a compact **Selected** composition summary, and the full composition reads back the same mode and five resources. Internal Prompt Seats remain in management surfaces instead of consuming conversation-entry width.
