# SillyTavern role-composition compatibility

Date: 2026-08-17. Status: implemented locally.

## Problem

The real Izumi preset enters roleplay in SillyTavern, but the earlier Harness adaptation retained definitions, order, and markers while registering all 53 System, 2 Assistant, and 1 User enabled entries as DSH System Prompt sections. `role="assistant"` was only a text attribute rather than an ST Assistant message. At the same time, native Session owned the `chatHistory` marker, post-history `{{lastUserMessage}}` became a placeholder, and DSH sent the actual user message only after the complete System Prompt. ST's `System → Assistant acknowledgement → User guide → System character/history/post rules → Assistant prefill → Generate` therefore became `one System string → current User → Generate`.

That difference made the internal author persona “Izumi/Konata/Master” in the preset's main task the clearest Assistant identity while Character Card remained later reference material. The real state proves Katisia markers at enabled order 105–109, but `💾主提示` at 40 explicitly says “you are Izumi”; Assistant boundaries on `接` and `卡思维链(K)` were also lost. A new Session did not automatically append Character Card `first_mes`, removing ST's character-history anchor as well.

## Decision

Source preset content and switches remain untouched. The Agent caches current user prose when `agent/inbox/claimed` claims it, allowing the first System Prompt assembly to expand the real `{{lastUserMessage}}`; later tool steps fall back to the latest native User message in Session. `renderPromptLayer` serializes imported User and Assistant definitions as `<st-user-message>` and `<st-assistant-prefill>`, while System and resource markers keep their existing tags. Fixed `st-role-protocol` uses order 990 to state ST message semantics, author personas as internal writing process, and the Binding's Primary Character as the visible Assistant identity; all 256 imported Prompt seats start at order 1000. If the selected order's final layer is Assistant Prefill, that layer maps to seat 255 at order 1255 and DSH Runtime Mode occupies order 1254 immediately before it. Tool requirements therefore stay near the generation tail while the preset's own Assistant Prefill remains the model's final System content. A Prefill containing an open planning, thinking, or reasoning tag does not enter the System carrier as continuable raw markup: compatibility serialization retains its complete escaped source under `visibility="private-reasoning"` and directs the Provider to apply it only in the reasoning channel.

When a composition first binds to a blank Session with no Transcript, Client automatically runs `rp-studio-opening` and appends `first_mes` as `plugin/recall` character history. Later applications never duplicate it. DSH's public extension still provides a System Prompt carrier, so this is explicit compatibility serialization rather than a claim that arbitrary intermediate Assistant/User messages were created.

## Verification

The real Izumi file proves 210 definitions, 177 order entries, 56 enabled entries, enabled roles of 53 System/2 Assistant/1 User, and `squash_system_messages=true`. Unit tests prove the new role tags, first-step expansion of claimed-but-not-yet-appended “你是？” at `lastUserMessage`, imported seats starting at order 1000, terminal Assistant Prefill at 1255, Runtime Mode at 1254, and escaped planning-prefill source with private-reasoning intent. The actual Tarball was installed into a disposable DSH home and exercised through the Codex in-app browser with the same Harness-adapted Izumi preset and Katisia. A new Session automatically received `first_mes`; first-step reasoning recognized Master's “你是？”, committed Katisia's world state, and then let Katisia introduce herself. RP Conversation attributed that body to Katisia, never presented Izumi, Konata, or Master as the visible character, and exposed no `konatan_planning` block. The preset's enabled input-expansion instruction still extends short input into story prose, as the source preset specifies; the compatibility layer does not remove it.
